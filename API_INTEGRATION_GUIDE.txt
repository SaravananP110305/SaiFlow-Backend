SaiFlow CRM – Mobile Developer Integration GuideThis guide is designed for Android, iOS, and cross-platform mobile developers integrating the SaiFlow CRM REST API.---1. Base URL & EnvironmentsDevelopment (Local Host): `http://localhost:5000/api/v1`Staging Server: `https://staging-api.saiflow.com/api/v1`Production Server: `https://api.saiflow.com/api/v1`---2. Authentication FlowSaiFlow implements standard JWT Access Token + Secure Cookie Refresh Token authentication.User Login: Call `POST /auth/login` sending `email` and `password`.Access Token Storage: On success, the API returns a short-lived `accessToken` in the JSON body. Cache this in the secure local key-store (Keychain for iOS, Shared Preferences / EncryptedSharedPreferences for Android).Session Cookies: The API response will contain a `Set-Cookie` header for a secure HTTP-Only `refreshToken` cookie. Make sure your HTTP client library (e.g. Retrofit, Alamofire, or Axios) enables cookie persistence (`withCredentials: true`).For all subsequent authenticated requests, attach the Bearer token in the headers:```httpAuthorization: Bearer <accessToken>```---3. Token Refresh & Rotation ProcessAccess tokens have a short validity period (e.g. 15 minutes). When an access token expires:The server returns a `401 Unauthorized` with the message `"Access token has expired"`.The client must call `PUT /auth/refresh` immediately to rotate session tokens. Ensure the HTTP client forwards stored cookies.The response will return a new `accessToken` which must be updated in local cache.Retry the failed original request with the new authorization header.---4. Common Response EnvelopeAll API responses follow a uniform structure represented by the server's `ApiResponse` wrapper.Success Envelope```json{  "success": true,  "statusCode": 200,  "message": "Resource retrieved successfully",  "data": { ... },  "meta": { ... }}````success`: Always `true` for success statuses (2xx).`data`: Holds the response payload (object or array).`meta` (Optional): Holds pagination indicators.Error Envelope```json{  "success": false,  "statusCode": 400,  "message": "Validation failed: Email is required"}```---5. Pagination & List Query ParametersAll list retrieval endpoints support dynamic pagination, sorting, and text searching:Query Parameters:`page` (integer, default: `1`): The target page index.`limit` (integer, default: `10`, max: `100`): The page size.`search` (string): Text filter query.`sortBy` (string): Target column name to sort by (e.g. `createdAt`, `title`).`sortOrder` (string): Direction `'asc'` or `'desc'`.Returned Pagination Metadata:```json  "meta": {    "total": 42,    "page": 1,    "limit": 10,    "totalPages": 5  }  ```---6. File Upload EndpointsFile uploads (e.g. PDF scope documents, spreadsheets, client requirements) are configured via standard HTTP multipart request parameters.Fields: Send files using `multipart/form-data` formatting containing the binary file stream under the key `file` or as specified in endpoints (e.g. `/leads/import` expects file input or a JSON payload depending on format).Storage: Uploaded files are hosted on cloud buckets or local static directories. File URLs are returned as full URIs in responses (e.g. `srsDocumentUrl`).---7. Error HandlingStatus codes used by the server to communicate request outcome states:`200 OK` / `201 Created`: Request succeeded.`400 Bad Request`: Input validation failed (Joi checks). Read the `message` field to display to the user.`401 Unauthorized`: Missing or invalid JWT or cookie. Trigger token rotation.`403 Forbidden`: Authenticated, but role does not possess permissions to write/modify this resource.`404 Not Found`: Target record ID or endpoint route does not exist.`409 Conflict`: Unique database constraints violated (e.g., email already in use).`500 Internal Server Error`: Critical backend crash or connection timeout. Show a generic error to the user.---8. Rate LimitingThe backend currently utilizes an unrestricted pass-through rate limiter (`rateLimiter.middleware.js`). However, clients should cache heavy assets locally and minimize redundant polling to prepare for potential production limits.
